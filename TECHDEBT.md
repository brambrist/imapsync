# Технический долг

Состояние на коммит с инкрементальной сверкой (`state_cache`). Сгруппировано по
приоритету. Пункты не упорядочены внутри группы строго.

## Архитектура и расширяемость

### A1. Вариативные источники синхронизации (один или оба конца — не IMAP)

Сейчас оба конца жёстко = IMAP: `syncer` напрямую работает с `*mailbox.Client`
(go-imap v1). Нет абстракции «конец синхронизации». На практике конец может быть:

- **IMAP** — есть;
- **Maildir** на диске — локально, без сети, чтение/запись файлов по maildir-спеке;
- **EWS** (Exchange Web Services) — SOAP/REST, когда IMAP на Exchange отключён или
  урезан по политике;
- потенциально JMAP, Gmail API, импорт из PST/mbox.

Нужно: интерфейс `Endpoint` (перечислить письма с их ключами, забрать письмо
целиком, дописать письмо, отдать аналог UIDVALIDITY), а `mailbox.Client` — одна
из реализаций. `syncer` работает только через интерфейс. Конфиг:
`server_a: { type: imap | maildir | ews, ... }`, тип на каждый конец независимо.

Тонкости миграции:

- дедуп-ключи (`Message-ID` / суррогатный хеш) от транспорта не зависят —
  переносятся как есть;
- запись `X-Imapsync-Hash` через append: Maildir — тривиально (пишем MIME-файл);
  EWS — проверить, можно ли добавлять кастомные заголовки через `CreateItem` с
  MIME-content;
- «UID» и «UIDVALIDITY» — IMAP-специфика. Для Maildir аналог — имя файла +
  inode/mtime, для EWS — `ItemId` + `ChangeKey`. Кэш состояния
  (`sync_endpoint` / `sync_msg_cache`) сейчас завязан на `uint32 uid` — нужно
  обобщить идентификатор письма до строки;
- `INTERNALDATE` и флаги — у каждого транспорта представлены по-своему.

## Критично до продакшена

### P1. `per_user_timeout` не прерывает висящий IMAP-вызов

go-imap v1 не context-aware; на операцию стоит статический
`client.Timeout = dial_timeout`. `ctx` проверяется только на контрольных точках
(между папками, каждые 64 письма). Зависший `FETCH` большой папки может выйти за
`per_user_timeout`, и тогда `sync_interval` не соблюдается. Нужен отдельный
короткий таймаут на I/O либо принудительное закрытие сокета по ctx.

### P2. Нет фолбэка по имени папки

`mailbox.FindFolder` написан, но не вызывается. `Select("Sent")` при реальном
имени `"Sent Items"` / `"INBOX.Sent"` / `"Отправленные"` → ошибка на всю пару
каждый цикл. Нужно использовать `FindFolder` (регистр/разделители) и, желательно,
автоопределение по `SPECIAL-USE` (`\Sent`).

### P3. Секреты только в открытом YAML

CLAUDE.md обещает «через переменные окружения» — не сделано. Нет `${VAR}`,
чтения пароля из файла / секрет-менеджера. Сейчас только `chmod 600`.

### P4. Один демон на одну БД без блокировки

Два запущенных инстанса на один sqlite побьют `sync_*` и `user_status`. Нужен
advisory-lock (PID-файл или лок на файле БД).

### P5. Нет ретраев на транзиентных ошибках

Обрыв соединения посреди юзера → ошибка, ждём следующего цикла целиком. Нет
бэкоффа, нет переподключения внутри цикла.

## Средний приоритет

### M1. Инкрементальный режим: нет периодического full-resync

Если кэш разъедется из-за бага, само не вылечится (только сброс БД или смена
UIDVALIDITY). Добавить `full_resync_every: 24h`.

### M2. Скопированное письмо не кладётся в кэш сразу

Нет `APPENDUID` (UIDPLUS) — в следующем цикле письмо перечитывается как «новое».
+1 `FETCH` на каждую копию, систематически.

### M3. `store` = `SetMaxOpenConns(1)`

Все операции БД со всех воркеров сериализуются через одно соединение. На большом
числе воркеров/юзеров — узкое место. WAL позволяет конкурентное чтение, лимит
можно поднять.

### M4. `copyOne` держит письмо целиком в памяти

`FetchFull` → `[]byte` → `InjectHashHeader` копирует ещё раз → `Append` из
буфера. Вложения на десятки МБ × воркеры = пики. Нет стриминга.

### M5. Коллизии суррогатного хеша

Date+Subject+From: письма без `Message-ID` с одинаковыми полями (рассылки,
автоответы) считаются дублями и не копируются. CLAUDE.md допускает расширение
состава — не сделано.

### M6. `insecure_tls` глобальный, не per-server

Нет STARTTLS (только implicit TLS 993), клиентских сертификатов, пиннинга.

### M7. `user_status` без истории

Перезаписывается каждый прогон. Нельзя увидеть, когда впервые сломалось / тренд.

### M8. Нет команд управления БД

Нет `db-remove-user` / `db-remove-folder`, нет очистки кэша одного юзера, нет
vacuum / ретенции `sync_msg_cache`.

## Низкий приоритет

### L1. `idx.Dups()` не выводится

Внутренние дубли папки считаются, но не попадают ни в stats, ни в лог.

### L2. Логи — плоский `log.Printf` в stderr

Без уровней (debug/info/warn) и структурного формата. Полагаемся на journald.

### L3. Нет метрик / healthcheck

Ни Prometheus, ни HTTP-эндпоинта состояния.

### L4. Дублируется разбор флага `-db`

В 5 подкомандах по-своему. Вынести общий парсинг.

### L5. `config.Duration` — только Unmarshal

Обратно конфиг не сериализуется.

### L6. go-imap v1 в maintenance-режиме

v2 активнее, но миграция большая (и CLAUDE.md явно требует v1).

## Тесты

### T1. Нет тестов в `cmd/imapsync`

CSV-импорт, диспетчер подкоманд, `db-list` со статусом — только ручная проверка.

### T2. Не покрыто

Сброс по UIDVALIDITY, реальный per-user timeout, отмена посреди FETCH, коллизии
суррогатного хеша.

### T3. Интеграция завязана на `go-imap/backend/memory`

Он не воспроизводит Dovecot/Exchange (SEARCH, APPENDUID, поведение флагов). Нет
теста против реального сервера (хотя бы в docker).

### T4. Нет бенчмарков

Гипотеза «инкрементально быстрее» не измерена количественно.
